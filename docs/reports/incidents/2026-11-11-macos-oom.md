# macOS out-of-memory crash in 0.1.3 and 0.1.4

On 2026-11-11, the live macOS app exited with a fatal Hermes out-of-memory error. The immediate problem was not visible in process RSS: Hermes's external-memory accounting grew during legacy Factory canvas draws while the JavaScript live set and RSS stayed nearly flat. This report separates the heap-cap stopgap from the draw-path mitigations.

## Timeline

| When | Event |
|---|---|
| 2026-11-11, 11:22:57 -0500 | A live 0.1.3 session launched. |
| 2026-11-11, 11:41:03 -0500 | About 18 minutes later, the session ended with Hermes out-of-memory (`GCBase::oom`) during canvas drawing. |
| 0.1.4 live use | A later release reproduced the failure after about 4 minutes. Process RSS was reported as roughly 173 MB and flat. |
| 0.1.4 rollback | The release was rolled back; the release process added a longer heap-aware soak rather than relying on RSS alone. |
| 0.1.5 work | Exact's native heap ceiling was raised to 512 MiB as a stopgap. Instrumentation tied the growth to frames drawn, and the old Factory surfaces stopped mounting on macOS. |

## Impact

The macOS client could terminate during a live session, before the planned soak duration. The failure affected live use of 0.1.3 and 0.1.4. The available evidence describes an app-process crash; it does not establish server impact or data loss.

## Root cause

Exact's native Hermes data module had a 64 MiB heap ceiling. Hermes OOM is fatal in this build. Exact also collects between module calls, so the JavaScript live set was observable separately from external bytes.

An instrumented 0.1.4 development reproduction showed:

- The JavaScript live set stayed around 9–12 MB.
- `js_externalBytes` rose about 0.13–0.15 MB/s, from 7.7 MB to 45 MB in 5.5 minutes.
- With approximately 250 frames per 15 seconds, the per-turn sample attributed about +21 MB to `factoryLive` and +10 MB to `factoryFloor`; collection between calls reclaimed about 38 MB. The estimate was roughly 85 KB of external allocation per drawn frame. With the old floor covered and no frames, external bytes stayed near 7.5 MB.
- Process RSS stayed near 173 MB, so the RSS trend did not expose the Hermes heap pressure.

The draw path exercised Exact's native recorder. A list `Writer` grew from a small ArrayBuffer by doubling and copying, then base64 used repeated string concatenation and the seam JSON-serialized another reply. The legacy floor drew frequently and amplified this per-frame churn. A later [isolated probe](https://github.com/couplet-physical-ai/switchyard/commit/a8c81d8) narrowed the persistent drift to legacy `factoryLive`: external bytes rose from 7.8 to 24.1 MB over 180 seconds while the berth board, Yard, and isolated string/ArrayBuffer/JSON/canvas probes stayed flat. That probe also found patch 0002 alone did not eliminate the legacy-floor drift. The supported conclusion is frame-driven external-memory growth in the old-floor path, not an unbounded world map or a demonstrated leak in every view.

## Fixes and mitigations

1. **Raise the ceiling, but do not call it the fix.** [`f8638ad`](https://github.com/couplet-physical-ai/switchyard/commit/f8638ad) added [patch 0001](../../reference/performance/exact-patches.md#patch-set), changing Exact's `DEFAULT_MAX_HEAP` from 64 MiB to 512 MiB. This provides headroom. It does not make Hermes OOM recoverable or prove memory plateaus.
2. **Reduce native recorder churn.** [`4e9b730`](https://github.com/couplet-physical-ai/switchyard/commit/4e9b730) added patch 0002: reuse the list writer and base64 scratch buffer, avoid per-character `+=`, and join the JSON reply once. The 78 tested replies matched the unpatched seam byte-for-byte. This is a general allocation reduction, not evidence that patch 0002 alone fixes the old floor.
3. **Stop drawing the implicated legacy surfaces on macOS.** [`8efbba8`](https://github.com/couplet-physical-ai/switchyard/commit/8efbba8) stopped mounting the old Factory versions on macOS. The later redesign [`c1626f0`](https://github.com/couplet-physical-ai/switchyard/commit/c1626f0) retired those floors from the product. The current rule is that an unchanged or covered canvas draws nothing.
4. **Measure the heap directly.** The app logs `heap: <live+external> MB · live <MB> · ext <MB> · cap 512 · frames <n>` every 30 seconds. Release soak checks this line, RSS, process liveness, the heap cap, and crash reports. Since 0.1.6 the release soak cycles Live, Factory, and Yard so each view is exercised; current gate details are in [`packaging/RELEASING.md`](https://github.com/couplet-physical-ai/switchyard/blob/main/packaging/RELEASING.md).

## What was rolled back

The 0.1.4 release was rolled back after the short-live OOM reproduction. The record does not show patch 0001 being reverted; the 512 MiB cap remained a native-build stopgap. Patch 0002 also remained useful for ordinary recorder allocations, but it was not treated as a standalone repair for the old floor after the isolated probe still saw drift there. The product mitigation was to stop mounting—and later remove—the old surfaces.

## Lessons

- RSS and JavaScript live bytes do not tell the whole memory story on Hermes. Track live plus external bytes, and keep the external component visible.
- Include the number of canvas frames in memory samples. No frames produced a different result from a frame-heavy view.
- A larger fatal-OOM ceiling buys time; it is not proof of a leak fix.
- Verify a recorder change at the byte boundary, then verify the actual affected view with a multi-view soak. A byte-identical patch can reduce churn without removing every source of external-memory drift.
- Idle is still: do not keep recording canvases when no real work changes their pixels.
